Sismo architecture note · Linux CPU profiling

Unwinding, module identity, fd retention, and symbolization

A linear account of what happens in BPF, what happens in runtime userspace, and what happens after recording—and how build IDs, file offsets, inodes, paths, and retained fds fit together.

The theory

  1. BPF captures a call chain and durable coordinates where possible.
  2. Runtime userspace improves the unwind and normalizes raw PCs.
  3. The trace stores module identity plus coordinates—not symbols or executable bytes.
  4. Optional retained fds keep exact local bytes alive until immediate symbolization.
  5. Post-processing finds trusted bytes, resolves coordinates, and appends symbols.

The canonical durable user frame is:

(build ID, ELF file offset)

Everything else exists either to produce that pair or to recover safely when it cannot be produced.

Vocabulary: what each identifier means

Build ID

Portable content identity for a particular binary. It does not contain symbols, locate bytes by itself, or keep a file alive.

File offset

A byte location inside that exact ELF file. Combined with a build ID, it is independent of ASLR and process lifetime.

Path

A display label and artifact-discovery hint. It is mutable, so it is never authoritative identity.

Device and inode

Local identity of the file object mapped by the target. Used to reject a pathname that now names a replacement.

Retained fd

A temporary lease on an inode. It keeps deleted bytes readable through immediate symbolization, but is never stored in the trace.

Synthetic ID

A recording-local stand-in for an id-less module. Useful for deduplication, but not for later artifact retrieval.

Build ID   = “which exact binary?”
File offset = “where inside that binary?”
Inode       = “which exact local file object?”
Fd          = “keep that local file object readable”
Path        = “what should humans see, and where should we look?”

1. Startup and lazy module inventory

Userspace runtimeStart without a mapping scan

The target is launched normally. The sample/retention pipeline does not eagerly inventory mappings or retain module files: it requests a mapping snapshot only after an actual sample exposes a new build ID or raw IP, or JIT/Python labeling needs one.

The in-kernel unwind-table loader is a separate control plane retained from the lightswitch unwinder: on x86-64 it inventories mappings and converts unwind tables before ticks can use them. That scan prepares unwind metadata only; it does not make any module fd retention-eligible.

When demanded, the scan records for each executable file-backed mapping:

  • mapping start and end;
  • mapping file offset;
  • module base;
  • device major/minor and inode;
  • display path;
  • GNU build ID, when readable.

The parser makes two passes: first to establish module bases and read each file’s build ID once, then to catalog executable mappings with complete metadata. Cataloging a mapping does not make it retention-eligible.

Cost: zero map work before the first relevant sample. A demanded scan is linear in that PID’s /proc/maps lines and executable mappings. Multiple new IDs in one sample share one scan; unresolved identities retry only under sample demand and the ordinary one-second cooldown.

2. Retention policy (executed lazily after a sample)

Userspace runtimePreserve bytes independently of frame identity

--keep-module-files=none|auto|all controls only fd retention. Build-ID capture remains enabled regardless of this policy. An fd is attempted only after that module appears in a CPU stack; unrelated mapped libraries are never retained merely because a map scan saw them.

PolicyBehavior
noneRetain no module files.
autoRetain unstable/local paths; normally skip system prefixes such as /usr, /lib, /bin, and /opt.
allRetain every eligible distinct inode.

The cap is 1,024 distinct inodes per recording.

Trust sequence

  1. Prefer opening /proc/<pid>/map_files/<start>-<end>.
  2. If denied, accept the display path only while its device/inode matches /proc/maps.
  3. After opening, verify device/inode again.
  4. When a real build ID is known, verify it through /proc/self/fd/N.

A failed open or identity check remains retryable. Policy refusals are permanent.

ModuleRegistry:
  (pid, base, device, inode) → settled ID, aliases, retained inode

Held files:
  (device, inode) → File

Symbolization view:
  build ID → /proc/self/fd/N

A late real build ID can become an alias for a previously synthetic registry identity—but only after the retained inode and real build ID are successfully reverified.

Key point: an fd is not identity. It is a temporary mechanism for keeping bytes available. The build ID remains the identity carried by durable frames.

3. BPF and perf-event setup

Userspace runtimeConfigure bounded kernel work

  • up to 12 performance counters;
  • up to 256 CPUs;
  • one 16 MiB ring buffer;
  • per-CPU on-CPU sampler links;
  • optional scheduler/futex/TCP/file off-CPU probes.

The old probe-side module-discovery ring and page-copy path are gone. BPF never parses ELF, scans /proc, resolves symbols, or retains module files.

4. On-CPU capture

BPF / kernelCapture a fixed, bounded record

  1. Read and advance at most 12 configured counters.
  2. Capture up to 64 raw kernel PCs.
  3. Capture up to 64 typed user entries with BPF_F_USER_STACK | BPF_F_USER_BUILD_ID.
  4. On default x86-64 capture, initialize the lightswitch-format in-kernel walker from the interrupted registers.
  5. Optionally capture up to 16 Python frame IDs.
  6. Submit one fixed-size ring record.

The typed user entry

status
20-byte build ID
file offset or raw IP
StatusMeaning
VALIDDurable (build ID, file offset).
IPThe helper could not produce durable identity; the value is a runtime PC.
EMPTYNo frame.

Raw-IP fallback covers anonymous/JIT memory, missing notes, mapping contention, and other helper limitations.

Dual-chain in-kernel unwind

The typed helper chain is always preserved as durable fallback identity. When the lightswitch-format walker completes—or a failed partial walk gets farther than the helper chain—BPF emits its selected raw PCs alongside that fallback. No user-stack byte snapshot is copied to userspace.

5. Off-CPU capture

BPF / kernelCapture at block; emit at wake

At voluntary switch-out, BPF stores:

  • timestamp and blocking identity;
  • up to 64 typed build-ID user frames;
  • up to 64 raw kernel PCs.

At switch-in it computes blocked duration and emits intervals of at least 10 μs. Pending states live in a 10,240-entry LRU map.

Off-CPU capture uses the typed helper chain directly. The lightswitch tail-call walker remains on-CPU-only because an off-CPU interval is captured from scheduler context and emitted later at wake.

6. Runtime worker and in-kernel unwind result

Userspace runtimeValidate and decode the chain already selected in BPF

A single Rust worker polls the ring, validates event type and exact record size, and decodes at most 64 typed entries:

VALID → BuildIdOffset(build_id, file_offset)
IP    → RawIp(pc)
EMPTY → discard

Plain and off-CPU samples proceed directly to frame normalization. For an in-kernel unwind result, userspace first observes every build ID in the embedded typed fallback so first-sample retention remains possible. It then emits the selected raw chain from BPF through the same normalization path.

completed lightswitch walk       → selected raw chain
failed walk farther than helper  → selected partial raw chain
otherwise                        → typed helper fallback

These authority rules are applied in BPF, not reconsidered by userspace. Build-ID/file-offset entries remain fallback identity and are never used as unwind inputs.

7. Normalize every user frame

Userspace runtimeConverge on one durable representation

Already a build-ID frame

No live mapping is required. Sismo stores Frame.rel_pc = file offset under a process-independent build-ID mapping.

Raw PC in a 20-byte-build-ID ELF

file_offset = mapping_file_offset + (pc - mapping_start)

The frame is converted to the same canonical build-ID/file-offset representation.

Raw PC in an id-less or nonstandard-ID file

The frame retains virtual-address semantics and receives a real nonstandard or recording-local synthetic identity.

Anonymous, JIT, or unmapped PC

Sismo may use residual mappings such as [jit:node], [anon], or [unmapped], with optional perf-map function names.

If no path is known for a real build ID, the durable display label is:

[buildid:<full 40-hex-character ID>]

8. Perfetto representation

Userspace runtimeIntern mappings, frames, and callstacks

Sismo hash-interns path strings, build IDs, function names, mappings, frames, and complete callstacks. On-CPU and off-CPU streams use separate IID namespaces.

Durable whole-file mapping

mapping identity: build ID
address_kind:     FILE_OFFSET
start/end/bias:   0
Frame.rel_pc:     original ELF file offset

Fallback virtual mapping

mapping identity: range + offset + base + path + ID
address_kind:     VIRTUAL_ADDRESS
Frame.rel_pc:     runtime virtual coordinate

The explicit address kind prevents a numeric file offset from being silently interpreted as a virtual address. A reused virtual range cannot inherit an old mapping IID because its full mapping identity participates in interning.

Per sample, native interning work is bounded by at most 64 user frames, 64 kernel frames, and 16 Python frames.

9. Shutdown and fd lifetime

Userspace runtimeDrain first; preserve the registry through symbolization

  1. Perform a final ring consume.
  2. Complete pending flush/stop acknowledgements.
  3. Join the worker.
  4. Destroy BPF links and close perf fds.
  5. Free the ring and BPF object.
  6. Return the fd-owning ModuleRegistry to the CLI.

The registry deliberately outlives BPF capture so retained module fds remain valid during immediate post-record symbolization.

10. Post-record symbolization

Post-processingQuery unique unsymbolized addresses

Sismo opens the trace in a fresh TraceProcessor and queries unsymbolized frames for:

mapping path
build ID
Frame.rel_pc
load bias
address kind

Rows are grouped by (path, build ID, load bias, address kind). Repeated samples at the same address collapse to one lookup.

If T is the number of frame rows and U is the number of unique module/address pairs:

trace collection: O(T)
symbol lookups:  O(U)

Post-processingSelect trusted executable and debug bytes

  1. Matching recorded path. Preferred so adjacent .gnu_debuglink, split-DWARF, and dSYM discovery remains available.
  2. Retained fd. Used when the original path is gone or replaced.
  3. Conventional build-ID locations. Such as /usr/lib/.build-id/xx/rest and /usr/lib/debug/.build-id/xx/rest.
  4. Debuginfod. Available when configured through DEBUGINFOD_URLS.
  5. Fail safely. A mismatching existing path is refused rather than mis-symbolized.

Executable bytes versus debug bytes

SourceResponsibility
Exact executable bytesTranslate file offsets through PT_LOAD; provide executable layout and format fallbacks.
Debug artifactProvide names, inline frames, source files, and line numbers.

A separate debug file is never used to interpret captured file offsets because its layout may differ from the executable.

Post-processingTranslate only for lookup

For a FILE_OFFSET frame, Sismo finds the file-backed PT_LOAD containing the offset:

lookup_vaddr = segment.p_vaddr + (file_offset - segment.p_offset)

The translated vaddr is used only by the symbolizer. The trace coordinate remains the original file offset.

Current cost detail: file-offset conversion currently constructs an ELF read view per unique sampled offset. Wholesym is loaded once per module, but ELF header/layout work is currently closer to once per unique FILE_OFFSET address. Parsing the layout once per module would be a straightforward future optimization.

11. Append and attach ModuleSymbols

Post-processingAttach names without rewriting frames

For each resolved original address, Sismo appends:

ModuleSymbols.path       = trace mapping path
ModuleSymbols.build_id   = trace mapping build ID
AddressSymbols.address   = original Frame.rel_pc

For FILE_OFFSET mappings, AddressSymbols.address is the original file offset—not the translated lookup vaddr.

Perfetto later attaches the symbol set by matching the mapping path, build ID, and original address. The captured frame is not replaced.

Symbolization is therefore additive: failure leaves the original build-ID/file-offset frame intact.

Disassembly limitation: FILE_OFFSET mappings currently receive symbolization but not assembly sidecars or static unwind diagnostics. Those paths remain limited to matching VIRTUAL_ADDRESS mappings so they cannot read replacement bytes or misuse coordinate semantics.

14. Design invariants

1. Capture coordinates, not symbols. BPF captures identity and location; symbols are a post-processing concern.
2. Prefer durable coordinates. Normal ELF frames should converge on (build ID, file offset).
3. Unwind quality and identity are separate. Unwinding chooses which frames exist; normalization chooses how they are represented.
4. An fd is an optimization, not identity. It preserves local bytes; the build ID remains the trace identity.
5. Paths are hints, never authority. A path is trusted only after identity verification.
6. Executable layout and debug information are separate. Executable bytes translate offsets; debug bytes provide names and lines.
7. Trace coordinates never change during symbolization. Lookup may use a translated vaddr, but attachment uses the original Frame.rel_pc.
8. Coordinate semantics are explicit. Every mapping says whether its frame coordinate is a virtual address or file offset.
9. Symbolization is additive. Failure does not destroy or rewrite captured identity.
10. Identity mismatches fail closed. No symbol is better than a confident symbol from the wrong binary.

15. The short explanation

On Linux, Sismo asks the kernel for a durable build-ID/file-offset helper chain. On x86 the in-kernel lightswitch-format walker may select a more authoritative raw chain, while preserving the typed helper chain for fallback identity and first-sample retention. Userspace maps selected raw PCs back to build-ID/file-offset pairs where possible and stores those coordinates with an explicit FILE_OFFSET mapping type. Separately, the recorder may retain verified module fds so deleted or replaced local binaries remain readable until immediate symbolization. After recording, Sismo finds trusted executable and debug bytes by build ID, converts file offsets through the executable’s PT_LOAD layout for symbol lookup, and appends ModuleSymbols keyed by the original path, build ID, and unchanged file offset. The fd is temporary; the build ID and offset are the durable trace identity.

This document describes the current uncommitted Linux implementation. Privileged runtime validation of all kernel and map_files configurations remains environment-dependent.
